# 讲义 01 · MySQL 索引与 B+ 树

> 用法：先通读一遍，然后合上这份文件，用手机录音讲 5 分钟。讲不下去的那句，就是没懂的那句。
> 文中所有具体数字我都标了「自己核」，你要去 `SHOW VARIABLES` 或官方文档确认一遍——面试被追问数字时答不上，比答错更伤。

## 一、为什么需要索引：一切都从"数据在磁盘上"开始

MySQL 的数据存在磁盘文件里，不在内存里。磁盘和内存的速度差了几个数量级，所以数据库的核心矛盾就一句话：**尽量少读几次磁盘**。

InnoDB 读数据不是一字节一字节读，而是按**页**（page）读，一页默认 16KB（自己核：`SHOW GLOBAL STATUS LIKE 'Innodb_page_size'`）。哪怕你只要一行 100 字节的数据，也得把整个 16KB 页捞进内存（Buffer Pool，就是数据库在内存里放数据页的缓存区）。

于是一张大表就是几十万个页。没有索引时查 `WHERE name='张三'`，只能从头到尾一页一页翻，这叫**全表扫描**。

索引的作用就是把"翻几十万个页"变成"翻三四个页"。

## 二、为什么是 B+ 树，不是别的

### 二叉查找树不行吗

二叉树每个节点只有两个分叉，一千万行数据要堆到 20 多层深。树每深一层，就多读一次磁盘页。深度就是命。

### 哈希表不行吗

哈希查等值确实快（一次定位），但两个致命问题：

一是**不支持范围查询**。`WHERE age > 20` 在哈希表里只能全表扫，因为哈希后的顺序和原始值大小无关。
二是**哈希冲突**退化时不可控。

所以 InnoDB 的索引默认用 B+ 树（自己核：MEMORY 引擎才默认用哈希索引）。

### B+ 树为什么矮

关键在**分叉数**。B+ 树的非叶子节点只存"键 + 指向下一层的指针"，不存数据。一个页 16KB，假设主键是 bigint 占 8 字节、指针占 6 字节，那么一个非叶节点能放 16KB ÷ 14B ≈ 1100 多个分叉（自己核这个算术）。

那么：

```
第 1 层（根）      1 个页 → 1100 个分叉
第 2 层         1100 个页 → 1100 × 1100 个分叉
第 3 层      121 万个页 → 存实际数据行
```

三层能支撑 **11 亿行级别**的数据量。也就是说，**再大的表，B+ 树也只有三层左右**，一次查询最多读 3 个页——而根节点和第二层节点几乎一定常驻内存，真正读磁盘的往往只有最下面那一层。

这就是"索引快"的全部秘密：**用极矮的树换极少的磁盘读取次数**。

### 叶子节点之间还有一条链表

B+ 树的所有叶子节点用双向指针串起来了。所以 `WHERE age BETWEEN 20 AND 30` 的做法是：先用树定位到 20 那个叶子（三次页读取），然后**沿链表横向走**，不用再回树上找 21、22。

范围查询高效就靠这条链。这是 B+ 树相对 B 树的一个重要设计（自己核：B 树非叶节点也存数据，所以分叉更少、树更高）。

## 三、聚簇索引和二级索引：叶子存的东西不一样

这是 MySQL 面试的最高频区。

**聚簇索引**（主键索引）：叶子节点存的是**整行数据**。所以"走聚簇索引查到行"是一步到位的。InnoDB 里一张表只有一棵这样的树，数据本身就按主键顺序排列存放。

**二级索引**（普通索引，比如 `INDEX(name)`）：叶子节点存的**不是整行，而是这一行的主键值**。

于是问题来了：

```sql
SELECT * FROM user WHERE name = '张三';
```

`name` 索引的叶子只告诉你"主键 id = 8"，你还得拿着 id=8 回到聚簇索引树上再查一遍，才能拿到那一行完整数据。

**这第二次查询就叫回表。** 回表是真实的性能开销，因为它意味着多走一遍树（最坏情况多几次随机 IO）。

### 覆盖索引：消灭回表

如果 `SELECT` 要的列，索引里已经有了，就不用回表：

```sql
-- 假设有联合索引 INDEX(name, age)
SELECT name, age FROM user WHERE name = '张三';
```

`name` 和 `age` 都在这个二级索引的叶子/键里，直接返回即可。`EXPLAIN` 的 `Extra` 列会显示 `Using index`，这就是覆盖索引成功的标志。

**面试加分说法**：为什么阿里规约里写"禁止 `SELECT *`"？除了浪费带宽，更实际的原因是 `SELECT *` 让覆盖索引失效，本来不回表的变成要回表。

## 四、最左前缀：联合索引为什么按顺序

`INDEX(a, b, c)` 的树是按什么排的？先按 a 排，a 相同再按 b 排，b 相同再按 c 排。像字典里 "abandon" 排在 "ability" 前面。

由此直接推出：

| 查询条件 | 能否用索引 | 为什么 |
|---|---|---|
| `a = 1` | 能 | 第一列有序，可定位 |
| `a = 1 AND b = 2` | 能 | a 固定后 b 是有序的 |
| `b = 2` | 不能（走不了这个索引） | b 在整棵树上完全无序 |
| `a = 1 AND c = 3` | 只用到 a | a 固定后 b 未知，c 就无序了 |
| `a > 1 AND b = 2` | 只用到 a | a 是范围，范围之后的 b 不再有序 |

最后一行是高频考点：**范围查询之后的列，索引用不上**。

同理，`LIKE '张%'` 能走索引（前缀确定，后面无序也无所谓），`LIKE '%张'` 不能（开头不定，整棵树的顺序帮不上忙）。

## 五、索引失效的常见写法

每一条都记住"为什么"，别背：

1. **对索引列做了运算或函数**：`WHERE YEAR(create_time) = 2026` —— 函数一算，原来的有序性全没了。改成 `create_time >= '2026-01-01' AND create_time < '2027-01-01'`。
2. **隐式类型转换**：列是 `varchar`，你写 `WHERE phone = 13800138000`（数字）。MySQL 会对**列**做转换，等价于给列套了函数，于是失效。这是线上最常见的隐形全表扫描。
3. **前缀通配** `LIKE '%xx'`。
4. **不满足最左前缀**（见上表）。
5. **`OR` 连接的两列中有一列没索引** —— 只能全表扫。
6. **字符集/排序规则不一致的关联查询**：`JOIN` 两表的字段一个 utf8 一个 utf8mb4，被关联列的索引可能用不上。

## 六、EXPLAIN 只看四列

不用会全部，面试够用就这四个：

- `type`：访问类型，从差到好大致是 `ALL`（全表）< `index`（扫索引树）< `range`（范围）< `ref`（非唯一等值）< `eq_ref` / `const`。看到 `ALL` 就该动手了。
- `key`：实际用了哪个索引。是 `NULL` 就是没用上。
- `rows`：预估要扫多少行。和结果集行数差几个数量级就有问题。
- `Extra`：`Using index` 覆盖索引成功；`Using filesort` 需要额外排序；`Using temporary` 用了临时表，通常也意味着要优化。

## 七、什么情况下索引会反过来害你

- **列的区分度太低**。`INDEX(gender)` 基本没用——一半一半的数据，走索引还得回表，比直接全表扫更慢。优化器会自己判断，所以它可能压根不走你建的索引。
- **索引建太多**。每个二级索引都是一棵独立的树，一次 `INSERT` 要同时维护所有树，写性能被换掉了。
- **前缀索引省空间但丢了覆盖能力**。`INDEX(email(10))` 只存前 10 个字符，能定位但不能直接返回完整值，必然回表。

## 八、和你项目的连接点（这块面试官一定会问）

你的知识库问答要用 pgvector 做向量检索。把它和 B+ 树放一起对比，你就同时理解了两个东西：

| | B+ 树索引 | 向量索引（HNSW / IVFFlat） |
|---|---|---|
| 回答的问题 | 这个值**等不等于** / 在不在某个**范围** | 这个向量**离谁最近** |
| 依赖的前提 | 数据能排出全序（谁大谁小） | 没有大小顺序，只有距离 |
| 结果 | 精确，要么在要么不在 | **近似**，可能漏掉真正的最近邻 |
| 代价 | 树高，几次 IO | 用召回率换速度 |

一句话：**B+ 树优化的是"找得到"，向量索引优化的是"找得够像"**。pgvector 的 HNSW 是一种多层图结构、IVFFlat 是先聚类再搜索，两者都是"牺牲一点准确性换大幅加速"——这和 B+ 树"用一次建树换永久有序"是完全不同的取舍思路。

这个对比你能讲出来，项目里"为什么用 pgvector、它和 MySQL 有什么不一样"这一问就稳了。
