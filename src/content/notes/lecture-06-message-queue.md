# 讲义 06 · 消息队列：削峰、解耦、不丢、不重、有序

> 用法同前五篇。这篇的"已核"部分来自 **RabbitMQ 官方文档**（`rabbitmq.com/docs/confirms`），我在正文里引了原话；Kafka 侧的参数名我给、**默认值一律留空**，因为我这次没查 Kafka 文档。
> 另外提醒：**面试你必须说清自己用的是 RabbitMQ 还是 Kafka**，两个的"顺序"和"不丢"机制不一样，混着说会被追着打。

---

## 一、先讲"直接调用会怎样"，MQ 的存在理由才立得住

没有队列时，A 服务调 B 服务是一根同步的绳子，三件事同时发生：

1. **峰值直接传导**：B 只能按自己的容量扛，10 倍流量来了就是打死 B（连带打死 B 依赖的数据库）。这就是"削峰"要解决的问题 —— 队列当一个**有缓冲的蓄水池**，B 按自己的节奏消费。
2. **强耦合**：A 必须知道 B 的地址、必须等 B 活着、必须处理 B 的超时和重试。B 加一个新的下游，A 要改代码 —— 这就是"解耦"要解决的问题（生产者只管把消息丢出去，谁关心谁订阅）。
3. **慢操作占用调用方**：一个 3 秒的操作（生成缩略图、调外部 API、算 embedding）同步做，会把上游的线程占住 3 秒 —— 直接接讲义 02 第六节：**同步 = 你的 Tomcat 线程在替下游买单。** 这就是"异步"要解决的问题。

三条各自的真实收益要说得出来，而不是并列背三个词：**削峰保护的是下游容量，解耦保护的是变更成本，异步保护的是线程资源。**

## 二、代价：为什么我要先说"你项目不一定需要它"

引入队列等于新增这些要维护的东西：

- **一套中间件集群**（它自己要高可用，讲义 04 那套主从/哨兵/副本问题它一个不少）；
- **最终一致性**：调用方拿到"已受理"，不是"已完成"。你的接口要能表达这个语义，前端要能查进度；
- **消息可能丢、可能重**：第三、四节整节在讲这个，**没有免费的午餐**；
- **调试链路变长**：一个 bug 现在要跨进程、跨时间看，日志必须靠 `traceId` 串起来；
- **事务边界被切断**：本地事务里"写库 + 发消息"做不到原子（除非用事务消息/outbox 模式，第四节讲）。

所以校招面试的正确姿势是：**能讲清机制，同时能讲清"我项目为什么没用"**。第八节给你现成的答法。

## 三、消息不丢：三段链路，每段单独问"这里怎么丢"

**生产端 → broker**

- RabbitMQ：开 **publisher confirms**。官方原话说得很准 —— 它覆盖的是 broker 侧的接收失败，**"they do not cover consumer processing"**；也就是说"确认收到了"绝不等于"处理完了"。
- Kafka：靠 `acks`（等几个副本确认）+ `retries` + 幂等生产者。**具体默认值我这次没查，你自己 `kafka-configs.sh --describe` 或看文档。**
- 通用的一条：发送失败要能重试，重试要有**上限和退避**（无限重试会把生产者线程拖死，讲义 02 的池就是这么被占满的）。

**broker 自身**

- RabbitMQ：消息要标记持久化、**队列也要是 durable**，两者都要满足才会落盘（只设一个等于没设，这条是经典考点）。
- **RabbitMQ 4.x 的默认队列类型是 quorum queues**，而 **classic mirrored queues（镜像队列）已经在 4.0 移除**（✅ 官方 `docs/quorum-queues`）。三个要点：quorum 队列基于 Raft 做副本；**重试上限用 `x-delivery-limit`，默认 20 次**（超过就按你的失败处理策略走，比如进死信）；官方明确 **quorum 队列不支持全局 QoS prefetch**（`global` prefetch 只有 classic 队列有）。**`x-single-active-consumer` 的默认值我这次没核到，见清单。**
- Kafka：靠**副本**。`min.insync.replicas` + `acks=all` 组合才谈得上"不丢"（**默认值我没能核实**，官方文档那页太长没取到，见清单）。
- 还要问一句：**broker 落盘之后，备份谁做？** 这跟讲义 04 第十节"副本不是备份"是同一件事。

**broker → 消费者**

- 官方明确警告：**automatic acknowledgement mode 是 "fire-and-forget" 并且 "should be considered unsafe"**。要"不丢"就得**手动 ack，并且处理成功之后才 ack**。
- 但"先处理后 ack"意味着**处理到一半崩了会重新投递** → 于是重复消费。这就是第四节的由来。
- 反过来"先 ack 后处理"就是丢数据的另一头。
- 还有个经典坑，官方原话：**"If all consumers requeue because they cannot process a delivery due to a transient condition, they will create a requeue/redelivery loop."** —— 处理不了就 `nack + requeue`，消息立刻回到队首，又被同一个人拿走 → **死循环打满 CPU**。解法是**退避重试 + 次数上限 + 死信队列**（第六节）。

## 四、重复消费与幂等：at-least-once 才是常态

先给结论，这是标准答法：**"消息队列只能给你 at-most-once / at-least-once 的保证；at-least-once 意味着必须重复消费，所以幂等是消费端的责任，不是队列的功能。"** RabbitMQ 官方文档就是这么写的："Consumers must be prepared to handle redeliveries and otherwise be implemented with idempotence in mind."

幂等的四种做法，按可靠性排：

1. **数据库唯一约束兜底**（最便宜、最可靠）—— 就是讲义 03 第十一节④：`(doc_id, chunk_no)` 建唯一索引，重复消息插进去直接冲突忽略。**先查再插不算幂等**，因为并发下两个都查到"没有"。
2. **业务状态机 + 版本号**：`UPDATE ... SET status='DONE' WHERE id=? AND status='PENDING'`，第二次执行影响 0 行，天然幂等。**这是我最推荐你写进项目的那种。**
3. **去重表 / 已处理 message_id 集合**：拿 `message_id` 做唯一键记录"处理过"。代价：这张表本身也要幂等写（回到第 1 条），而且要清理。
4. **天然幂等的操作**：`set` 类（覆盖写）、按 id 更新为固定值 —— 注意 `INCR` **不**幂等，重复一次就多算一次。

顺带一个真问题：**"写库成功但 ack 失败"** → 消息被重投 → 靠幂等挡住；**"ack 成功但本地事务回滚"** → 消息丢了 → 要靠"先提交事务再 ack"或者 outbox 模式（把"要发的消息"当业务表的一行，和主事务一起提交，再由后台任务投递）。**能讲 outbox，你就从"会用 MQ"跨到"知道分布式一致性难在哪"了。**

## 五、顺序性：全局顺序是奢侈品

**为什么需要顺序**：同一个订单的"创建 → 支付 → 退款"三条消息乱序消费，状态就错了。

**为什么全局顺序贵**：要保证全局有序，只能**一个队列 + 一个消费者**，于是并发度和吞吐直接归一 —— 你用 MQ 本来就是为了并发。

**工程上的答案：把"需要顺序"的范围缩小到单个业务实体**。

- Kafka：**同一 partition 内有序**。所以按业务 key 分区（`key = orderId`），同一个订单的消息自然落到同一分区、按序消费；不同订单之间无所谓顺序 —— 这叫分区级有序。
- RabbitMQ：一个队列只有被**单个消费者**消费时才有顺序保证；多消费者会并发取走。**具体行为和 `x-single-active-consumer` 这类参数名你去官方文档核**。
- 消费端自己也会**破坏顺序**：拿到消息后丢进线程池并发处理，顺序立刻没了。解法是**按 key 做哈希分派到固定的处理线程/队列**（同 key 同线程，不同 key 并行）。

一句总结：**"我不保证全局有序，我保证同一业务实体有序。"**

## 六、积压、重试与死信

**积压**（队列越堆越长）是症状，原因通常是消费速度 < 生产速度。要会讲三步：

1. **先判断是消费者挂了还是真流量涨了**（看消费速率和错误率，别看队列长度猜）。
2. **限流入口 + 扩消费者**。扩消费者之前先确认瓶颈在消费者 CPU/IO 还是在下游数据库 —— 如果是数据库，加消费者只会把数据库打得更死（讲义 02 第六节的木桶，一模一样）。
3. **追不上的部分**：提高并发、临时降级非核心消费者、批处理合并、或者按业务决定"丢弃旧的"（例如行情类消息只关心最新值，积压的可以直接丢）。

**prefetch / QoS**（RabbitMQ）：控制一个消费者最多同时在手多少条未 ack 消息。**官方明确说 prefetch 设 0 表示 "no limit"**，也就是无限拉到本地 → 内存风险，而且消息被"占着"却还没处理，消费者崩了时要整体重投。

**死信（DLX）与重试退避**：处理失败 → `nack + requeue=false` → 进死信交换机 → 由死信队列/延迟重试队列接住，按退避策略再投。**必须有重试次数上限**，超限进死信并**告警**。没有上限的重试是事故放大器。

## 七、什么情况下会坏

1. **消息体塞太大**：把整篇文档 / 整个列表丢进消息。正确做法是**只放 id 和必要的元信息**，消费者自己去查（讲义 04 的大 key 是同一个道理）。
2. **没有重试上限 / 没有死信告警**：错误消息在队列里无限循环，或者悄悄堆到十万条没人知道。**监控 lag 和死信数量是上线前的必备项。**
3. **改了分区数/队列数**：Kafka 加分区会**打破已有的 key→partition 映射**（同一 key 的新旧消息落到不同分区，顺序保证失效，且 rebalance 期间消费停摆）。这是典型的"改一个配置引发线上事故"。
4. **消费者组频繁再平衡**：消费者启停、处理超时（超过 `max.poll.interval.ms` 这类参数，**具体名字和默认值留空**）都会触发 rebalance，期间整组不消费。
5. **把 MQ 当数据库用**：队列不是存储，堆积的"待办"最终应该在业务表里有状态可查。
6. **事务边界搞混**：`@Transactional` 方法里发消息，事务还没提交消息就已经被消费方拿走（消费方读库读不到那条数据）。这是**你项目里真会写的 bug** —— 解法是事务提交后再发（`TransactionSynchronization` / 事件监听在 afterCommit 阶段）。

## 八、和你项目的连接点

**① 你现在不需要 MQ，理由要能说清。** 你的知识库问答是单机、几个人用、批量导入是可控的离线动作。判断标准是：

> 只有当我需要"**把峰值交给下游按自己节奏消化**"或者"**多个互不相识的下游订阅同一件事**"时，我才引入队列。我现在两条都不满足，加了只会多一个要运维的进程。

被追问"那什么时候需要"，给得出临界点：**多实例部署、导入耗时不可控（分钟级）、要接第三方回调、或者同一事件有多个订阅方。**

**② 你真正需要的是"队列的三个性质"，可以用现成的东西拿到。**

- **失败重试 + 断点续传**：文档表加 `status`（PENDING / RUNNING / DONE / FAILED）+ `retry_count`，导入任务只捞 PENDING，失败就 `retry_count++`，超限标 FAILED 等人工。**这就是 W7 那格我写的项目动作。**
- **"数据库当队列"**：`SELECT ... WHERE status='PENDING' FOR UPDATE SKIP LOCKED LIMIT 10` —— `SKIP LOCKED`（MySQL 8.0 起支持，PostgreSQL 也有）让多个 worker 各拿各的行、互不阻塞。**这个方案零新增组件，可靠性还是数据库给的。** 面试讲得出这一条，比讲"我用 RabbitMQ 搭了个 demo"强得多，因为它证明你知道**代价**。
- **Redis 当队列的取舍**：`LPUSH` + `BRPOP` 很简单，但它的可靠性上限就是讲义 04 讲的那套 —— 异步复制、everysec 的 1 秒窗口、AOF rewrite。**所以 Redis 队列适合"丢了能重来"的任务，不适合账单类任务。** 一句话：**"要可靠用数据库，要快用 Redis，要解耦和多订阅方才上 MQ。"**

**③ 如果真要用，选哪个。** 给你一句能讲的取舍：**Kafka 的强项是高吞吐、顺序（分区级）、可重放（消息按位点保留，能倒回去重算）；RabbitMQ 的强项是路由灵活、低延迟、开箱即用的死信/重试语义。** 我的项目是低吞吐 + 需要路由和重试语义 → 选 RabbitMQ；日志/事件流分析类 → Kafka。

**④ 把讲义串起来的一条主线（面试可直接用）**：削峰的本质是**缓冲**（讲义 02 的队列）→ 消息**不丢**的本质是**日志与副本**（讲义 03 的 redo/binlog、讲义 04 的 AOF/主从）→ 幂等的本质是**唯一约束**（讲义 03 ④）→ 顺序的本质是**分区键**（讲义 04 Cluster 的 hash tag 与槽）。这四句连着讲，你的知识是网，不是点。
