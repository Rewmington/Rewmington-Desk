# 讲义 05 · Redis 缓存三兄弟、分布式锁与缓存一致性

> 用法同前四篇：先通读，再合上文件录音讲 5 分钟。
> 这篇的"已核实"只有少数几条来自 RabbitMQ/Redis 官方文档，其余是行业共识做法 —— 我照旧在末尾分成 **✅ 已核** 和 **⚠️ 留空** 两类。**没核实的别当数字背。**

---

## 一、先承认一件事：缓存的"快"就来自不一致

缓存和数据库是**两份数据**。只要接受这一点，很多问题就通了：

- 你不可能既让缓存独立存在、又让它和库每毫秒都一致。所有"一致性方案"做的都是**选择那个不一致的时间窗口有多长、以及窗口内读到旧数据业务能不能忍**。
- 面试标准答案的骨架就一句：**"我不追求强一致，我追求最终一致 + 可控窗口"**，然后讲你的窗口是多少、怎么收窄、读到老数据会怎样。

三兄弟（穿透、击穿、雪崩）说的是另一件事：**缓存本来该挡住的那部分流量，反过来把数据库打死了**。它们的共同机制是一句话——**没命中 ≠ 数据不存在**。数据库的容量假设建立在"大部分请求被缓存挡住"上，一旦这个假设破了，DB 就是主角。

## 二、穿透：查的是根本没有的东西

**成因**：请求的 key 在缓存里没有，在库里**也没有**（比如 `id=-1`、一个不存在的商品编号、被人构造出来的随机 id）。于是每次请求都**穿过**缓存直达数据库，缓存对这个 key 毫无作用。数据库查完还是空，什么也没缓存下来，下次继续穿。

三种治法，各有代价，必须成对讲：

1. **缓存空值**：查库发现没有，就往缓存写一个 `nil` 占位，**配一个很短的 TTL**（一两分钟量级，具体看你的数据会不会"后来出现"）。
   - 代价：内存被无效 key 占住；**第一次仍然打库**（只能挡住连续同 key 的重复穿透）；如果攻击者每次换 key，这个方案完全无效。
2. **布隆过滤器拦在前面**：把"确定存在的 id"全集放进去。它的性质要背准 —— **"说不存在"一定不存在；"说存在"可能是误判**。所以它只能挡在数据库前面做拒绝，不能做真相判断。
   - 代价（这三个坑能讲出来才叫懂）：**不支持删除**（标准布隆过滤器只能置位不能清位。官方文档直接点名的替代是 **Cuckoo filter —— 它支持删除**，检查更快但插入更慢）；重建要扫全量；误判率一旦超过设定值不会报错，只会**越来越脏**。
   - 数字（✅ 已从官方 Bloom filter 文档核对）：最优哈希个数 `k = ceil(-ln(p) / ln(2))`；每元素所需位数 `-ln(p) / ln(2)^2`。官方给的对照表：**1% → 7 个哈希、9.585 bit/元素；0.1% → 10 个、14.378 bit；0.01% → 14 个、19.170 bit**。它还算了对比：如果用 Redis Set 存，内存是 `capacity * (192b + value)`，举例 IP 地址约 40 字节/条 —— **比 0.01% 误判率的布隆过滤器贵一个量级**。
   - 用法（✅ 已在 Redis 开源版内，不再是单独的 RedisBloom 模块）：`BF.RESERVE key 0.001 1000000 [EXPANSION n] [NONSCALING]`，然后 `BF.ADD` / `BF.MADD` / `BF.EXISTS` / `BF.MEXISTS`。**容量要估准**：低估会自动叠加子过滤器（官方原话：增加操作延迟，因为要先查最上层、返回"没有"再往下查）；高估浪费内存。默认 `EXPANSION = 2`；官方建议"元素数未知就用 ≥2，已知就用 1 省内存"。`NONSCALING` 还能少用一个哈希函数。
   - **一句自己的算术**（不是官方数字，是我按公式推的，你可以复核）：100 万个文档 id、误判率 1%，约 `1e6 × 9.585 bit ≈ 9.6 Mbit ≈ 1.15 MB`。也就是说挡穿透的成本几乎可以忽略 —— 这正是"该用布隆就别犹豫"的理由。
3. **入口校验**：参数合法性在 Controller 层就拒掉（非数字、越界、负 id）。这不是"高深方案"，但线上大量穿透就是这么来的。

## 三、击穿：一个热 key 到期的那一下

**成因**：**单个热点 key** 过期瞬间，成千上万的并发请求同时 miss，全部涌向数据库。跟穿透的区别就在数量级：穿透是"查不存在的"，击穿是"存在的、但恰好这个 key 失效了"。

三种治法：

1. **互斥重建**：miss 之后不是所有人都去查库，而是**先抢一把短锁**，抢到的那个查库 + 回填 + 释放，其余的**等一下再读缓存**（或者先返回兜底数据）。
   - 代价：多一次等待、多了锁的超时与失效问题（第五节全在讲这个）、代码路径变复杂。**注意它只保护回填路径，别把业务读逻辑也塞进锁里。**
2. **逻辑过期**：key **不设 TTL**，而是在 value 里带一个 `expireAt`。读到 `expireAt` 已过时，**先把旧值返回**，同时丢一个异步任务去重建。
   - 代价：**读到的一定是旧的**（这是设计目标而非 bug，你要说清业务能不能忍）；需要额外线程池；如果重建一直失败，你会永远读到旧数据 —— 必须加告警。
   - 适用：真正的大热点（首页商品、秒杀），宁可旧也别打穿。
3. **永不过期 + 定时刷新**：由写入方（或定时任务）主动更新缓存，读方不负责重建。最省心，代价是多了个后台链路，数据变更要能被它知道。

## 四、雪崩：一大片同时失效，或者 Redis 整体没了

**成因**两种，一定要分开讲：

- **TTL 集中到期**：批量预热时给所有 key 设了同一个过期时间，到点一起失效。**这是最常见的自造雪崩。**
- **Redis 实例/集群不可用**：缓存层整体下线，全部流量直接砸到数据库，同时可能还有重试的客户端在放大流量。

治法与代价：

1. **TTL 加随机抖动**（`base + random(0, N)`）—— 成本几乎为零，收益最大，**这是默认该做的一件事**。
2. **Redis 高可用**：主从 + 哨兵，或者 Cluster —— 这些的机制和**官方原话的坑**都在讲义 04，这里只说选型：**高可用解决"实例没了"，解决不了"一大片 key 同时过期"**。
3. **限流与降级要当成一等公民**：数据访问层里明确写死"缓存未命中且数据库并发超过阈值 → 直接返回兜底/降级"，而不是让线程无限排队。没这一条，缓存挂了就是整站挂。
4. **多级缓存**：进程内缓存（Caffeine 这类）挡在最前面。代价：本地缓存不共享、失效更难，**多实例之间会短暂不一致**（第八节讲）。
5. **冷启动预热**：Redis 重启后是全空，此时所有请求都算 miss。别在低峰期让流量自己填，要有主动预热。

## 五、分布式锁：三个条件必须同时成立

面试只要问"你项目里怎么保证不重复处理"，你就得把这段说清楚。锁的最低要求是三条：

1. **互斥**：任意时刻只有一个持有者。
2. **不会永久持有**：持有者崩了，锁能自动释放（超时）。
3. **只能持有者释放**：不能删别人的锁。

### 演进过程（这段按顺序讲，是最容易加分的写法）

```
v1  SETNX lock 1                     →  加锁成功后进程崩了，锁永不释放：死锁
v2  SETNX lock 1 + EXPIRE lock 30    →  两条命令不原子：加完锁还没设过期就崩，还是死锁
v3  SET lock <唯一值> NX EX 30       →  原子了。但业务超过 30 秒时锁自动过期，
                                        B 拿到锁，A 跑完执行 DEL → 把 B 的锁删了
v4  SET ... NX EX  +  Lua 校验后再删  →  value 必须是本次持有的唯一标识，
                                        "判断归属"和"删除"必须在同一个脚本里原子完成
```

v3 那条 `SET key value NX EX seconds` 里的 NX / EX 选项组，官方命令页标注 **since 2.6.12**（✅ 已从 `redis.io/docs/latest/commands/set/` 核对；同一页还给了 KEEPTTL = 6.0.0、GET / EXAT / PXAT = 6.2.0、**IFEQ / IFNE / IFDEQ / IFDNE = 8.4.0**）。v4 的解锁写法现在分新旧两代（✅ 官方分布式锁页原文）：

```
DELEX key IFEQ my_random_value        # Redis 8.4 起，官方页给出的解锁命令
```

8.4 之前用 Lua，官方给的形状就是这一条，调用形式 `EVAL ...script... 1 resource-name token-value`：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

官方对 token 的要求写得很具体：**这个值必须"在所有客户端、所有加锁请求之间都唯一"**，它建议 **20 字节的 `/dev/urandom`**，也允许"微秒时间戳拼 client ID"这种更便宜的做法，并自己评价说"not as safe, but probably sufficient for most environments"。为什么不能用固定值或者只用客户端 id：同一个客户端会**先后两次**持有同一把锁，第二次拿到锁后，第一次那次迟到的解锁会把第二次的锁删掉 —— 官方举的例子正是"客户端拿到锁后卡在临界区超过锁有效期，回头把别人已经拿到的锁删了"。

另外一条常被讲错的：官方说的是"因为 SET 的这些选项已经能替代 `SETNX` / `SETEX` / `PSETEX` / `GETSET`，**将来某些版本可能**把它们废弃并最终移除" —— 是"将来可能"，不是"已经废弃"。

### 剩下的两个问题，v4 也解决不了

### 官方自己怎么定性"基于故障转移的方案不够"（✅ 原话，这段直接背）

《Distributed Locks with Redis》专门有一节 **Why Failover-based Implementations Are Not Enough**，它给的竞态就是四步，结尾四个大写单词：

```
1. 客户端 A 在主机上拿到锁
2. 主机在把这个 key 的写入传给副本之前崩了
3. 副本被提升为主
4. 客户端 B 拿到了同一个资源的锁   →  SAFETY VIOLATION!
```

但官方紧接着给的取舍很有分寸，这句一定要连着讲：**"Sometimes it is perfectly fine that, under special circumstances, for example during a failure, multiple clients can hold the lock at the same time. If this is the case, you can use your replication based solution."** —— 也就是说：**如果你的业务能接受"故障期间可能两个人同时持锁"，主从方案就够用；不能接受，才往下走。** 这不是"单实例不安全所以别用"，而是"按你的容忍度选"。

### 剩下的两个问题，v4 也解决不了

- **锁提前过期（业务比 TTL 长）**：TTL 设短了业务没跑完锁就没了，设长了崩溃后要干等。官方的说法是**扩展锁**：客户端在有效期内快用完时，用一段 Lua 脚本"值仍是我的随机值才把 TTL 重新设回去"，并且**续期也要在多数节点上成功才算续到**；同时官方警告续期次数必须有上限，否则破坏活性。工程上常见的**看门狗**（Redisson 这类 Java 库后台自动续期）就是这个思路的实现 —— **它是第三方库的行为，不是 Redis 的机制，默认周期我没能核实，别背网上流传的 10 秒 / 30 秒。**
- **进程停顿 / 时钟问题**：官方在 **Disclaimer about consistency** 里点名两件事，这是我见过的最值钱的两条提醒 ——
  1. **"You should implement fencing tokens."** 锁服务发一个**单调递增的序号**，客户端把序号带给被保护的资源，资源方拒绝比它已知序号更旧的请求。这样即使锁失效、即使进程 GC 停顿了很久，迟到的持有者也写不进去。官方还补了一句"别假设只要进程还活着锁就还在"。
  2. **Redis 的 TTL 不用单调时钟**，所以**改系统时间（哪怕 NTP 校正）可能让同一个锁被两个进程同时持有**。这条是从机制层面解释"为什么锁不可靠"。

  所以标准答法是：**"能讲出 fencing token，说明我知道锁本身不可靠，正确性要靠被保护的资源兜底。"**

### Redlock：官方给的算法与它的假设（✅ 全部原话）

官方假设 **N 个完全独立的 Redis master**（不复制、不互相同步），例子里 **N=5**，要跑在不同物理机/VM 上。加锁五步：

```
1. 取当前毫秒时间戳
2. 并行地向 N 个实例用同一个 key、同一个随机值加锁（SET ... NX PX），
   每个实例用远小于总有效期的超时（官方举例：有效期 10 秒，单节点等待 ~5–50ms）
3. 若 >= 多数（至少 3）成功，且总耗时 < 锁有效期  →  算拿到
4. 有效期 = 初始 TTL - 已耗时
5. 失败（没拿到多数，或算出来是负数）→ 把所有实例上的锁都释放（包括自认为没锁上的）
```

官方给的安全下界：**`MIN_VALIDITY = TTL - (T2 - T1) - CLOCK_DRIFT`**（T1=开始询问第一个节点的时刻，T2=收到最后一个节点回复的时刻），并说明在这段时间内多数 key 同时存在，所以别的客户端不可能同时凑齐 N/2+1。重试要**随机延时**（避免两个客户端互相抵消造成"谁都赢不了"）；网络分区时要付**等于 TTL 的可用性代价**，连续分区可以无限期不可用。

它还有一个很硬核的点：**Redis 挂了重启后可能让互斥被破坏。** 官方的分析是——完全不开持久化时，某个持锁节点重启后就"失忆"，同一个资源可能再次被 3/5 锁上；开了 AOF 且**默认每秒 fsync**，掉电重启后那个 key 也可能没了；**要抵御任意重启场景，理论上得把 fsync 设成 always**（性能代价明显）。但它同时给出一个便宜的替代：**让崩溃过的实例延迟重启 —— 离线时间超过你用的最大 TTL**，等老锁全部自然失效再回来，这样"不开持久化也能保住安全"（代价是可用性）。这段能讲出来，说明你真读过而不是背八股。

**争议部分**（官方页面自己列在 Analysis of Redlock 一节，两条链接都在）：Martin Kleppmann 的批评 **http://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html** 与 antirez 的回应 **http://antirez.com/news/101**。我的转述是二手，**面试别说死，去读原文**（尤其 Kleppmann 关于 GC 停顿与时钟漂移的反例，以及"Redlock 不是共识算法"这个论点）。

**什么时候真的需要分布式锁**：多实例跑同一个定时任务、防止同一订单被并发处理、扣减库存的读-改-写。反过来说 —— 有唯一索引能挡的重复，用唯一索引更便宜（讲义 03 第十一节④）；而对"绝对不能双写"的场景，官方在 Disclaimer 里指向的是 fencing token 这类资源侧机制，而不是把锁当成正确性的来源。

## 六、缓存与数据库一致性：把四个方案摆开对比

前提：**大多数业务用"先更新数据库，再删缓存"（Cache Aside）**。为什么是"删"而不是"改"缓存？

- 并发写会让缓存里的值**乱序**：两个事务都更新库，然后都写缓存，后写的可能覆盖成先那个的旧值；
- 大部分 key 其实不会被读到，**算好塞进缓存是浪费**，删除则把成本摊薄到真被读的时候（惰性加载）。

| 方案 | 流程 | 漏洞 |
|---|---|---|
| 先删缓存，再更新库 | 删 → 写 | 删完到写完之间，别人读到库里的旧值并**回填**进缓存，脏数据长期存在 |
| **先更新库，再删缓存**（推荐） | 写 → 删 | 极端情况仍有窗口（读写并发下小概率时序不巧），但概率远低于上一行 |
| 延迟双删 | 删 → 写 → 等一会儿 → 再删 | "等一会儿"要等多久？等于一次读+回填耗时，是**估的**；治标 |
| 订阅 binlog 异步删缓存 | 写库 → canal 拉 binlog → 删缓存 | 业务代码不感知缓存，链路解耦且不会漏；代价是**多一个组件**（它和讲义 07 的主从复制是同一份 binlog） |

三条一定要能各答一句：

1. **兜底是 TTL**：任何不一致都应该在 TTL 到期时自动收敛。所以"缓存多久过期"其实是你的**最长不一致时间**，这个数字要能说出来。
2. **强一致要锁，代价太大**：把"更新库 + 更新/删缓存"包在分布式锁里，等于用第五节那套不可靠的机制去做正确性保证 —— 通常不划算。
3. **读旧数据的后果是什么**：这是面试官真正想问的。价格、库存、余额 → 后果重，要收窄窗口甚至不走缓存；文章、配置、统计 → 忍得住。**答案在业务侧，不在技术侧。**

## 七、什么情况下会坏（汇总，能当 checklist 用）

1. **只加缓存不加保护**：没做 TTL 抖动、没做互斥重建、没做限流降级 —— 三个兄弟里的任何一个都能打穿你。
2. **命中率当效果**：命中率 95% 但剩下 5% 全是大查询，照样能把库打死。要量的是**回源 QPS** 和**回源耗时**，不只是命中率。
3. **空值缓存被恶意打爆**：攻击者用海量不同 key 打穿透，你缓存的空值反而把 Redis 内存撑满（还接讲义 04 的淘汰策略：`maxmemory` 到了会把你真正的热数据淘汰掉）。
4. **大 key 当缓存值**：把整个列表/整篇文本序列化进一个 key，网络传输 + 单线程序列化一起拖住 Redis（讲义 04 第十节）。
5. **锁 TTL < 业务耗时** → 双持锁 → 数据重复处理。
6. **忘在 finally 里释放锁**，或者 DEL 用在了 Lua 校验之前。
7. **更新库成功、删缓存失败**，代码没重试也没兜底 → 不一致窗口变成"直到下次过期为止"。
8. **两级缓存的失效只做了一层**：本地缓存收不到失效通知，跨实例永远对不齐。

## 八、和你项目的连接点

**① 检索结果缓存怎么设计。** 你的知识库问答里最贵的一步是 embedding + 向量检索。缓存对象应该是**检索结果**而不是答案：

```
key    = kb:ret:{sha1(query + topK + 过滤条件)}
value  = 命中的 doc_id + chunk_id 列表（不是整段文本）
TTL    = 5~15 分钟 + 随机抖动
```

只存 id 列表的理由：文本块本身在 pgvector 里已经有了（缓存一份是浪费内存，讲义 04 第九节的"只放能重建的东西"）；而且文档更新时你只需要按 id 反查影响面。**这条设计能直接回答"缓存什么、缓存多久、不一致了会怎样"三层追问。**

**② 文档更新后怎么让缓存失效 —— 这是你项目里真实存在的难题。** 你没法从"doc 123 更新了"反推出哪些 query 的缓存命中了它。三条路，各有代价：

- **等 TTL 自然过期**（最简单，窗口 = TTL；能忍就选它，把 TTL 当成你的不一致窗口说清楚）；
- 缓存 key 里带上**文档集合版本号**，改动时把版本号 +1 → 老 key 整体作废（代价：命中率瞬间归零，等价于一次小雪崩，要预热）；
- 用 Redis 的 **Set 建反向索引**（`doc:123 -> {kb:ret:xxx, ...}`）精确删（代价：反向索引本身要维护、会膨胀，且这是"多一个要维护的东西"）。

**这道题没有正确答案，只有能讲清代价的选择** —— 面试要的就是这个。

**③ 拒答也要缓存。** "检索不到就明确拒答"这个结论，对同一个 query 是稳定的：把它当空值缓存（短 TTL），既省一次 embedding 调用，又正好是第二节"缓存空值"的落地。

**④ embedding 结果缓存。** key 用 `model_id + sha1(text)`（换模型必须换 key，否则维度对不上）省 API 钱。但**算一下内存**：1024 维 float32 ≈ 4KB/条，10 万条 ≈ 400MB —— 你 `maxmemory` 配多少、会不会因此把检索结果缓存淘汰掉（第七节第 3 条），这是能拿出来讲的真实权衡。

**⑤ 单机场景不要分布式锁。** 你现在只有一个进程，互斥用 Java 的锁就行（讲义 02）。什么时候才需要：**多实例部署同一个定时重建任务**、或者用户重复提交同一份文档。面试答法："我的服务是单实例，用进程内锁；**如果扩到多实例，我会先用数据库唯一约束兜底，还解决不了才上 Redis 锁，并且承认它在主从切换下可能失效。**" —— 这句比"我会写 Redlock"高一个层次。
