## 一、为什么需要事务：从"一半失败"推起来

一张表里扣钱和加钱是两个动作。第一条成功、第二条失败（程序崩了、磁盘满了、被 kill 了），账就平了——这是业务不能接受的。所以你需要一个东西，把多条语句捆成**一个不可分割的单位**：要么全成，要么全当没发生过。

但"不可分割"不是事情的全部。还有第二个问题，很多人背八股时把它漏了：

**就算每个事务内部都是原子的，多个事务同时跑，结果也可能不对。**

你读一行数据的读到一半，别人把它改了，你拿到的是"半新半旧"的行；你为了统计而扫全表，扫的过程中有人 INSERT 了一行，你的统计到底算不算那行？这就是**并发正确性**问题，跟原子性是两码事。事务这个概念同时管这两件事：

- 原子性 → 靠 **undo log**（回滚日志，记录"怎么撤销"）
- 并发正确性 → 靠**锁 + MVCC**（多版本并发控制）

顺带把第三个日志放进来：

- 持久性 → 靠 **redo log**（重做日志，崩溃后能"重放"出来）
- 复制与恢复 → 靠 **binlog**（归档日志，逻辑层记录所有改动）

**四个词（ACID）不是四个特性清单，是四种"坏了怎么办"的方案**。面试说"原子性靠 undo、持久性靠 redo、隔离性靠锁和 MVCC"，比背"Atomicity、Consistency……"高一档。

## 二、并发会出哪三种乱：脏读、不可重复读、幻读

这三个名词必须按"哪个动作引发的"来理解，不能按顺序背：

**脏读（dirty read）**：你读到了别人**还没提交**的数据。最典型的用法是读用户的库存数，然后按这个数下单——结果那个事务回滚了，你依据一个从未存在过的值做了决定。所以"能读到未提交"这个级别（读未提交）在生产上基本没人用。

**不可重复读（non-repeatable read）**：同一个事务里，**同一句 SELECT 执行两次，结果不一样**。原因是别的事务在中间改了这行并且提交了。注意它跟脏读的区别：脏读读到的是"没提交的内容"，不可重复读读到的是"别人已经提交的改动"，只是这个改动来在你两次读之间。

**幻读（phantom read）**：同一个事务里，两次**范围查询**，第二次多出来（或少了）几行，像出现幻觉一样。原因是别的事务 INSERT / DELETE 了符合你条件的行。

一句抓住本质：**不可重复读是 UPDATE 造成的，幻读是 INSERT / DELETE 造成的**。丁奇那本书里就是按这个角度切的——这也是它比大部分八股文讲得准的地方。

## 三、四种隔离级别：只记"谁挡得住谁"

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 代价 |
|---|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 基本没人用 |
| READ COMMITTED（RC） | 挡住 | 可能 | 可能 | Oracle / PostgreSQL 默认 |
| REPEATABLE READ（RR） | 挡住 | 挡住 | **InnoDB 基本挡住** | **MySQL InnoDB 默认** |
| SERIALIZABLE | 挡住 | 挡住 | 挡住 | 读也加锁，并发度极差 |

怎么背得住：**隔离级别越高 = 读得越少 = 越慢**。RR 的"可重复"三个字就是承诺——你一个事务里两次读同一行，结果一定一样。代价是你读到的可能是几秒前的世界。

要会说的取舍：为什么互联网大厂很多把 MySQL 从默认的 RR 改成 RC？因为 RC 只用行锁、不加间隙锁（官方原话：RC 下 "InnoDB locks only index records, not the gaps before them"，并且 "Because gap locking is disabled, phantom row problems may occur"），**并发更高、死锁更少**；代价是官方文档写死了 "Only row-based binary logging is supported with the READ COMMITTED isolation level"——用 RC 就只能吃 row 格式的 binlog，日志量比 statement 大。这种"知道选另一条路要付什么"的话，比背四个级别值钱。

## 四、MVCC 想解决什么：读的人别等写的人

最粗暴保证隔离的办法是：谁在写，别人就都别读。那数据库就没法用了——一个长事务在改一行，所有查询全卡住。

MVCC 的思路是**别互相等，让大家读各自该读的版本**：

- 一行数据被改过多次，就同时存在多个版本，用 **undo log 串成一条版本链**：最新版本在数据页里，旧版本顺着 undo 往回找，每个版本头上挂着"是哪个事务把我改成这样的"（trx_id）。
- 一个事务开始读的时候，拍一张"**当前谁还没提交**"的快照，叫 **ReadView**。
- 然后沿着版本链从新到旧走，**找到的第一个"对我可见"的版本**，就是这条 SELECT 的结果。

于是读写不冲突了：写的人改最新版，读的人在版本链上找一个旧版。**这就是"不加锁也能隔离"**，也是 InnoDB 大部分读操作并发性好的根本原因。

## 五、可见性判断只有四条规则

ReadView 里记着：`creator_trx_id`（我自己是谁）、`m_ids`（快照那一刻还没提交的事务 id 列表）、`min_trx_id`（列表里最小的）、`max_trx_id`（下一个将被分配的 id）。

拿着版本链上某个版本的 `trx_id` 去比（书里对应位置，按你发的目录：**`trx_id` 分配规则**在第 12 章「大家别误会，「MVCC」只是「读视图」(ReadView)策略」的那节「trx_id分配规则」；**可见性比较**在同一章「MVCC下不同版本直接比较的结果」；**各隔离级别怎么找记录**在第 14 章「不同隔离级别下的一致性读会有什么坑」的「各隔离级别下访问表时寻找用户要的记录的过程」和「多版本并发控制」）：

1. `trx_id == creator_trx_id` → 是**我自己**改的 → 可见。这条很重要，不然你写完自己还读不到旧值，逻辑直接乱。
2. `trx_id < min_trx_id` → 这个事务在我拍快照之前就**已经提交**了 → 可见。
3. `trx_id >= max_trx_id` → 这个事务在我拍快照之后才开启 → 不可见。
4. 落在 min 和 max 之间 → 去 `m_ids` 里查：**在**（说明它还没提交）→ 不可见；**不在**（说明它已提交）→ 可见。

不可见就顺着 undo 链往下一个版本走，直到找到可见的。

## 六、RC 和 RR 的唯一区别：ReadView 拍几次

这是整篇最值钱的一句话，也是最能区分"背过"和"懂了"的一条：

- **RC**：事务里**每执行一条 SELECT 语句，都重新拍一张 ReadView**。所以别人一提交，你下一条 SELECT 就看到了 → 于是有不可重复读。
- **RR**：只在事务里**第一次 SELECT 时拍一张**，之后所有 SELECT 都用这张。所以别人的新提交你永远看不见 → 于是可重复读。

机制完全相同，锁也基本相同，就差"快照拍几次"。这一条讲清楚了，别人会认为你真读过。

注意"第一次 SELECT"这个措辞——它意味着 **`BEGIN` 本身不拍快照**，只有真的做了一次一致性读才拍。这正是下面那个实验会撞到的点。

## 七、动手：两个终端，20 分钟，做完这一节才算读通

开两个 MySQL 客户端，都先执行：

```sql
CREATE TABLE acc (id INT PRIMARY KEY, balance INT);
INSERT INTO acc VALUES (1, 100);
```

终端 A 里跑这一串（**顺序不能变**）：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN;
SELECT * FROM acc;          -- ① 看到 100，此刻 A 拍了 ReadView
```

切到终端 B：

```sql
UPDATE acc SET balance = 200 WHERE id = 1;   -- 直接执行，B 是自动提交
```

回到终端 A：

```sql
SELECT * FROM acc;          -- ② 还是 100 —— 这就是可重复读
UPDATE acc SET balance = balance + 1 WHERE id = 1;
SELECT * FROM acc;          -- ③ 变成 201！不是 101
COMMIT;
```

**③ 才是这题的重点**：A 的 SELECT 一直看到 100，可它自己的 UPDATE 却作用在 200 上（结果 201）。因为 UPDATE 是**当前读**，读的是最新版；SELECT 是**快照读**，读的是版本链上对我可见的旧版。**同一个事务、同一行数据，两种读看到的是两个世界。**

把隔离级别换成 RC 再跑一遍，②就会变成 200。再做一个变体：A 先 `BEGIN` 但**不做 SELECT**，让 B 改完提交，A 再 SELECT ——这次 A 看到的是 200，因为它的 ReadView 是在 B 提交之后才拍的。

## 八、快照读 vs 当前读，以及 RR 到底有没有解决幻读

- **快照读**：普通的 `SELECT`，走 MVCC 版本链，不加锁。
- **当前读**：`SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`（8.0 里也可写 `FOR SHARE`，自己核语法版本）、以及任何 `UPDATE` / `DELETE` / `INSERT` —— 读的是**最新版本**，并且要加锁。

于是 RR 有没有解决幻读，取决于你从哪个角度问：

- 只用快照读：**解决了**。两次范围查询结果一样（都靠同一张 ReadView）。
- 快照读之后又来一次当前读（比如上面那个 UPDATE）：**没解决**，你会"发现"一行自己看不见的行被改了——③ 那个 201 就是这个现象。

InnoDB 在 RR 下的做法是加 **next-key lock（记录锁 + 间隙锁）**：你按一个范围做当前读或更新时，它不仅锁住匹配的行，还锁住行与行之间的那个**间隙**，别的事务想往这个空隙里 INSERT 就得等。所以"别人插不进我要扫的范围"，从**写**这一侧把幻读挡住了。

诚实的结论，也是面试最好的答法：**RR 通过 MVCC 挡住了快照读路径上的幻读，通过间隙锁挡住了当前读路径上的幻读；但把一个快照读和一个当前读混在同一个事务里时，仍然能观察到幻读。**

顺带一个高频追问：*间隙锁只在 RR 有，RC 没有。* 这是"大厂改成 RC"最实际的动机之一。

## 九、redo / undo / binlog 为什么要三个

把 WAL（Write-Ahead Logging，先写日志再改数据）这条链走一遍，三个日志各自的活就清楚了：

1. 事务要改某行，先在内存（Buffer Pool）里改数据页，改之前把改动写进 **undo log**（记"怎么回到改之前"）；
2. 把对应的 **redo log** 写进 log buffer，在事务提交时刷盘（redo 是**顺序写**，所以提交很快；脏数据页可以晚点再刷回磁盘，那是 checkpoint 的事）；
3. 同时往 **binlog** 写一条"这条数据变成了什么"，提交时刷盘。

redo 是 InnoDB 引擎内部的物理日志（内容固定、循环写）；binlog 是 MySQL server 层的逻辑归档（追加写，可以无限长，主从复制和"恢复到某时刻"全靠它）。两份日志必须都对，否则会出现"引擎改了但归档没记上"这种灾难。所以 InnoDB 用**两阶段提交**把它们绑在一起：redo 先 prepare → 写 binlog → redo 再 commit。崩溃恢复时以 binlog 为准来判断该提交还是回滚（自己核这个恢复规则）。生产上追求最强一致性的配置是"双 1"：`innodb_flush_log_at_trx_commit = 1` 且 `sync_binlog = 1`（自己核这两个参数的默认值和性能代价）。

一句话分工：**undo 保原子，redo 保持久，binlog 保复制与恢复，两阶段提交保这三份东西不打架。**

## 十、什么情况下会坏

1. **长事务**。它一直持有那张旧 ReadView，undo 版本链就一直是长的、清理不掉；它还占着锁；它还会通过 **MDL 元数据锁**把你后面一个本来很快的 `ALTER TABLE` 堵死，而所有新查询又排在 ALTER 后面——一个忘了 commit 的终端能引发整站不可用。这是真实事故里最常见的一种。查它：`SELECT * FROM information_schema.INNODB_TRX ORDER BY trx_started;`（自己核这个视图的列名）。
2. **大事务**。一条 `DELETE` 删一百万行：undo 巨大、binlog 单条巨大、主从延迟飙升、回滚成本极高（回滚通常比执行还慢）。做法是分批、每批一个事务。
3. **WHERE 没走索引 → 锁范围爆炸**。InnoDB 锁的是它扫到的记录，没索引就意味着扫全表，于是你把整张表的行都锁了，别人全堵。这是"一个慢 UPDATE 引发雪崩"的标准成因，也直接连回讲义 01 的索引失效。
4. **死锁**。两个事务以相反顺序更新两行。InnoDB 有检测（`innodb_deadlock_detect`，自己核默认值），检测到就**回滚其中一个**而不是傻等；另一个报错 `Deadlock found when trying to get lock`。看原因：`SHOW ENGINE INNODB STATUS;` 里的 `LATEST DETECTED DEADLOCK` 段，配合 `innodb_print_all_deadlocks` 把死锁全打进错误日志。
5. **等锁超时**。默认 `innodb_lock_wait_timeout = 50` 秒（自己核）。**报错不一定是死锁，也可能只是有人占着锁不放**——把这两种混起来说，面试会被追打死。

## 十一、和你项目的连接点

**① `@Transactional` 的默认回滚规则。** 遇到 `RuntimeException` 和 `Error` 才回滚，遇到**受检异常不回滚**。你写 `try { 插入向量表; } catch (IOException e) { throw new IOException(); }` 时，数据其实已经留在库里了。要么用 `rollbackFor = Exception.class`，要么别抛受检异常。**这个坑每个用 Spring 的人都会踩一次，你能提前讲出来就是加分。**

**② 自调用不走代理。** 同一个类里的 A 方法调 B 方法，B 上的 `@Transactional` **不生效**，因为 Spring 的事务是靠代理实现的，内部调用没经过代理。你批量导入文档时最容易这么写。

**③ 事务边界怎么切。** 你那个"读目录 → 切块 → 调 embedding → 写 pgvector"的流程：一次 LLM/embedding API 调用要几百毫秒到几秒。**绝不能把网络调用包在事务里**，否则连接和锁被这几秒全程占着——正好是第十节第 1 条的自造版。正确切法：算向量的过程放在事务外，只有**写库那一段**开事务；一批 N 条一个事务，而不是 1000 条一个。

**④ 幂等靠唯一约束，别靠"先查再插"。** "启动时只查不重算"这个逻辑，并发或重启两次时，先查再插是有窗口的（两个线程都查到"没有"，然后都插）。给 `(doc_id, chunk_no)` 或文件 hash 建唯一索引，让数据库替你挡，冲突就忽略或更新。**这就是隔离性在你项目里的直接落点。**

**⑤ 你的向量库是 PostgreSQL，不是 MySQL——面试一定会追这一刀。** 千万别把 MySQL 那套原样搬到 pgvector 上说。先把两个我之前跟你讲过的说法修正准确：**PostgreSQL 的默认隔离级别是 READ COMMITTED，不是"快照隔离"**；它的 RC 是**语句级快照**（一条语句内结果一致，语句之间能看到别人的新提交），而 PG 的 REPEATABLE READ 才是**事务级快照**——"拍几次快照"这个分界在两个数据库里是同一条线，很好记。往下三处必须讲出不同：

- 版本存储：InnoDB 用 undo 版本链、原地更新；PG 把新元组**另写一份**，旧元组标记为已死，靠 **VACUUM** 回收。
- 由此推出一条运维差异：PG 里一个**长事务会让全库停住清理**，死元组堆起来、表膨胀、查询变慢——比 MySQL 的 undo 变长更凶。
- RR 下的冲突处理：MySQL 靠间隙锁把插入堵住；PG 的 RR 不拦写入，但事后会直接抛 **serialization failure** 让应用重试（自己核这两个说法，官方文档 InnoDB Locking / Transaction Isolation 两节，以及 PostgreSQL 的 MVCC 与 Locking 两节，都能查到）。

一句话总结这两个库的哲学：**MySQL 宁可让你等，PG 宁可让你重试。** 你能讲出这句，"为什么用 pgvector、它和 MySQL 有什么不一样"这个问题就彻底站住了。
